An action is a program. When a workflow step calls it, the runner starts it as one process, gives it its inputs as a JSON file, and reads its outputs from another. The contract is the same for every language.

## What the action receives

The runner sets these environment variables. Each names a file or folder.

| Variable | Content |
|---|---|
| `BENTRA_INPUT_FILE` | JSON object with the step's inputs |
| `BENTRA_OUTPUT_FILE` | Where the action writes a JSON object of outputs |
| `BENTRA_AUTH_FILE` | JSON object with the step's `module.auth`: `type` plus that method's fields. Not set when the step passes no auth |
| `BENTRA_CONTEXT_FILE` | `{run_id, job_id, workflow_id, step: {id, name, index}, module: {name, version, action}}` |
| `BENTRA_STEP_OUTPUTS` | JSON object of the outputs of earlier steps, keyed by step `id` |
| `BENTRA_MODULE_DIR` | The module's package, to read files you shipped with it |
| `BENTRA_TEMP_DIR` | Scratch space, deleted when the action ends. `HOME` and `TMPDIR` point there too |

The action starts in an empty scratch folder, not in the module's folder. Use `BENTRA_MODULE_DIR` to find your own files. A file the action writes can be at most 2 GiB.

<Note>
An action doesn't receive the workflow's variables, secrets or form answers. It gets only what the step passes as `inputs` and `auth`. Its environment contains `PATH`, locale, proxy and certificate settings, and the variables above.
</Note>

## Outputs

Write one JSON object to `BENTRA_OUTPUT_FILE`. It must match the action's `outputs` schema and be at most 1 MB.

```json
{"status": 200, "ok": true, "elapsed_ms": 141}
```

Later steps read these values with `${{ steps.<id>.outputs.<name> }}`.

To keep an output out of the logs, mark it in the schema:

```yaml
outputs:
  type: object
  properties:
    session_token:
      type: string
      x-bentra-secret: true
```

## Success and failure

- Exit code `0` means success. Any other exit code fails the step.
- To explain a failure, write an `error` object before exiting:

```json
{"error": {"code": "not_found", "message": "No item named demo"}}
```

The message appears in the run's log.

## Logging

Anything the action prints to stdout or stderr becomes log lines on the run page. Secret auth fields and secret outputs are replaced with `***`. Still, don't print credentials.

## Credentials

Declare the methods the module accepts under [`auth`](/reference/module-syntax#auth) in `module.yaml`. Read credentials only from `BENTRA_AUTH_FILE`: check `type` to see which method the step chose, then read that method's fields. The file is readable by the runner's user alone and is deleted when the action exits. Never write credentials into the module's repository.

```python
import json, os

auth = {}
if os.environ.get("BENTRA_AUTH_FILE"):
    with open(os.environ["BENTRA_AUTH_FILE"]) as f:
        auth = json.load(f)

headers = {}
if auth.get("type") == "token":
    headers["Authorization"] = f"Bearer {auth['token']}"
```

## Timeouts

An action is stopped when it runs longer than its limit, along with every process it started. The limit is the first of these that is set: the step's `timeout_minutes`, the action's `timeout_seconds`, the module's `defaults.timeout_seconds`. It can't exceed the runner's own step timeout.

## Languages

Set `runtime.language` in `module.yaml`.

<Tabs>
<Tab title="Python">
```yaml
runtime:
  language: python
  version: ">=3.11"
dependencies:
  file: requirements.txt
```
Entrypoints are `.py` files. The runner creates a virtual environment for this module version with uv and installs the requirements file into it with `uv pip install -r`. Pin the packages (`requests==2.33.0`) so every install is the same. If the runner has no Python matching `version`, it installs one with uv, so any version uv can install works.
</Tab>
<Tab title="Bash">
```yaml
runtime:
  language: bash
```
Entrypoints are run with `bash`. Bash modules can't declare a dependency file: use tools the runner already has, ship what you need in the folder, or install it with a [setup script](#setup-script).

```bash
name=$(jq -r .name "$BENTRA_INPUT_FILE")
echo "Hello $name"
jq -n --arg greeting "Hello $name" '{greeting: $greeting}' > "$BENTRA_OUTPUT_FILE"
```
</Tab>
<Tab title="Node.js">
```yaml
runtime:
  language: node
  version: ">=20"
dependencies:
  file: package.json
```
Write entrypoints as **CommonJS** (`.js` or `.cjs` with `require`). Commit `package-lock.json` beside `package.json`; packages are installed with `npm ci --omit=dev` and found through `NODE_PATH`, which `require` uses and ES module `import` ignores.

```javascript
const fs = require("fs");
const inputs = JSON.parse(fs.readFileSync(process.env.BENTRA_INPUT_FILE, "utf8"));
fs.writeFileSync(process.env.BENTRA_OUTPUT_FILE, JSON.stringify({ greeting: `Hello ${inputs.name}` }));
```
</Tab>
<Tab title="Compiled (Go, Rust, …)">
```yaml
runtime:
  language: binary
  platforms: [linux-amd64, linux-arm64]
actions:
  - name: deploy
    description: Deploy a release.
    entrypoint: deploy
```
Build your program for each platform and commit the executables as `bin/<platform>/<entrypoint>`, for example `bin/linux-amd64/deploy`. They must be marked executable in Git.
</Tab>
</Tabs>

For Node.js and Bash, a runner can only run a module whose runtime it has. See [Modules on runners](/runners/modules).

## Setup script

`setup` in `module.yaml` is a bash script the runner runs once when it builds the module version's environment, after the dependency install. It doesn't run on every call. Use it to install a tool your actions call:

```yaml
runtime:
  language: python
  version: "3.13"
dependencies:
  file: requirements.txt
setup: |
  uv pip install example-cli==1.2.3
```

The script runs in the module's folder with the environment active, so `uv pip install` installs into the module's virtual environment. Anything it puts in the virtual environment's `bin` or in `$BENTRA_ENV_DIR/bin` is on the action's `PATH`. Bash and compiled modules can have a setup script too. See [`setup`](/reference/module-syntax#setup).

Nothing is installed when you release. The environment is built on a runner, in the **Prepare modules** step, the first time a job uses the version. To change the dependencies or the script, bump `version`.

## Private packages

The dependency install and the setup script don't receive the workflow's variables. List the ones they need in `dependencies.env`:

```yaml
dependencies:
  file: requirements.txt
  env: [UV_INDEX_URL, PACKAGE_TOKEN]
```

The runner passes those names from the calling workflow's variables and secrets, so each workflow that uses the module defines them, for example a variable `UV_INDEX_URL` pointing at `https://packages.example.com/simple/`. Actions never receive them.

Pass credentials to installers through these environment variables only. Don't write them into a config file inside the environment: the build fails if it finds a passed secret there.

## Test an action locally

The contract is plain files, so you can run an action on your own machine. The [example repository](https://github.com/bentraLLC/bentra-module-examples) has `scripts/run-action.sh`, which sets up the files and variables the way a runner does, installs the module's dependencies in a scratch folder and prints the outputs. Copy it into your repository:

```bash
scripts/run-action.sh path/to/module my_action path/to/module/tests/my_action.json path/to/auth.json
```

Or by hand:

```bash
export BENTRA_INPUT_FILE=$(mktemp) BENTRA_OUTPUT_FILE=$(mktemp) BENTRA_AUTH_FILE=$(mktemp)
echo '{"url": "https://example.com"}' > "$BENTRA_INPUT_FILE"
echo '{"type": "token", "token": "…"}' > "$BENTRA_AUTH_FILE"
python actions/check_url.py && cat "$BENTRA_OUTPUT_FILE"
```
