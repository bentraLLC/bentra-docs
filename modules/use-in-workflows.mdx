---
title: "Use modules in workflows"
description: "Call a module action from a workflow step, pass inputs and credentials, and read outputs."
---

A workflow step runs a script (`run`), calls a module action (`module`) or triggers a [GitHub Actions workflow](/reference/workflow-syntax#github-actions-steps).

```yaml
name: "Check and record a service"
steps:
  - id: service
    name: Make a service name
    module:
      name: text-tools
      version: "1.0.0"
      action: slugify
      inputs:
        text: ${{ inputs.service_name }}

  - name: Check its endpoint
    module:
      name: http-check
      version: "2.0.0"
      action: check_url
      auth:
        type: token
        token: ${{ vars.MONITORING_TOKEN }}
      inputs:
        url: https://${{ steps.service.outputs.slug }}.example.com/health
```

## Find a module and its actions

Open **Modules** and choose a module. The **Actions** tab lists each action with its inputs and outputs, and **Copy step** gives you a step to paste into `workflow.yml`.

## Step fields

| Field | Required | Meaning |
|---|---|---|
| `module.name` | yes | The module's name in the registry |
| `module.version` | yes | An exact released version, in quotes. No ranges and no `latest`. **Add module step** fills in the module's active version |
| `module.action` | yes | The action to run |
| `module.auth` | if the module requires auth | `type` (one of the module's methods) and that method's fields. See [Authentication](#authentication) |
| `module.inputs` | if the action requires inputs | Values for the action's inputs |
| `id` | to read outputs later | A name for the step: lowercase letters, digits and underscores |
| `if` | no | A [condition](/reference/workflow-syntax#steps--if). The step runs only when it is true |
| `timeout_minutes` | no | Stop the action after this long (1 to 1440). Never longer than the runner's own step timeout, 5 minutes by default |
| `continue_on_error` | no | Keep going if the step fails; the run still ends failed |

## Inputs and expressions

Input values can be written out or filled in when the run happens:

| Expression | Value |
|---|---|
| `${{ inputs.<field> }}` | A form answer, or a variable given when a job is triggered |
| `${{ vars.<NAME> }}` | A workflow or collection variable |
| `${{ steps.<id>.outputs.<name> }}` | An output of an earlier step with that `id`: a module step or a [`run` step](/reference/workflow-syntax#step-outputs) |

An input that is exactly one expression keeps its type, so a number stays a number. Inside a longer string the value becomes text:

```yaml
inputs:
  replicas: ${{ inputs.replicas }}
  name: "${{ inputs.team }}-${{ inputs.environment }}"
```

`${{ }}` works inside `module.inputs` and `module.auth`. A step's [`if`](/reference/workflow-syntax#steps--if) is a separate expression.

## Authentication

A module never stores credentials. Its **Authentication** tab lists the methods it accepts, and the step passes one of them in `module.auth`:

```yaml
    module:
      name: http-check
      version: "2.0.0"
      action: check_url
      auth:
        type: token
        token: ${{ vars.MONITORING_TOKEN }}
```

| Method `type` | Fields |
|---|---|
| `token` | `token` (secret) |
| `basic` | `username`, `password` (secret) |
| `api_key` | `key` (secret) |
| `oauth2_client_credentials` | `client_id`, `client_secret` (secret), and optionally `token_url` and `scope` |
| a custom method's name | The fields the module declares |

- A secret field must be exactly one `${{ vars.<NAME> }}` or `${{ inputs.<field> }}`: a secret [variable](/guides/variables-and-secrets), or a form field such as a password the requester fills in. Never write the value in `workflow.yml`.
- Other fields can be written out or use `inputs.` and `vars.` expressions. Step outputs can't be used in `auth`.
- The runner masks the secret fields in the run's logs and outputs.
- To rotate a credential, change the variable. Nothing needs republishing.
- When the module's auth is optional, leave `auth` out to call it without credentials.

## Outputs in script steps

A `run` step can read what earlier steps returned from the JSON file at `$BENTRA_STEP_OUTPUTS`, keyed by step `id`:

```yaml
  - name: Report
    run: |
      jq -r '.service.slug' "$BENTRA_STEP_OUTPUTS"
```

## What Bentra checks when you publish the workflow

Publishing a workflow version (or syncing a repository workflow) fails, naming the step and line, when:

- the module or version doesn't exist, or the version was revoked;
- the action doesn't exist in that version;
- a required input is missing, or a written-out value has the wrong type;
- an expression isn't one of the three forms, or refers to a step that doesn't come earlier;
- the module requires auth and the step passes none, or the module takes no auth and the step passes some;
- `auth.type` isn't one of the module's methods, or a field is missing or unknown;
- a secret auth field isn't a single `vars.` or `inputs.` expression.

A deprecated version is allowed, with a warning.

## Versions stay fixed

A workflow version runs exactly the module versions it names. A newer module release changes nothing until you edit the workflow to use it. Each run records the module versions and package checksums it used.

To move a workflow to a new module version, change `version` in `workflow.yml` and publish the workflow.
