Most modules will be written by a coding agent (Claude Code, Cursor, Copilot and others). An agent writes good modules when it knows three things up front: the layout Bentra expects, the exact `module.yaml` rules and the action contract. This page gives you all three in a form you can hand over directly.

## 1. Give the agent the context file

Save this as `AGENTS.md` (or `CLAUDE.md`, `.cursor/rules/bentra-modules.md`, … whatever your agent reads) at the root of the repository that holds your modules. It is the same file as [`AGENTS.md` in the example repository](https://github.com/bentraLLC/bentra-module-examples/blob/main/AGENTS.md).

````markdown AGENTS.md
# Building Bentra modules

Instructions for coding agents writing [Bentra](https://bentralabs.com) modules. Copy this file
into your repository (as `AGENTS.md`, `CLAUDE.md` or your agent's equivalent) and keep it next
to your modules.

A **module** is a versioned package of **actions** that Bentra workflow steps call. It lives in
one folder of a Git repository (its **working directory**), is registered in an organization's
private registry, and is released as immutable versions that workflows pin exactly.

## Rules

1. **The working directory is the boundary.** Bentra lists, reads and packages only the module's
   folder and what is nested in it. Nothing outside exists for the module: no `../` paths, no
   shared code in a parent folder, no symlinks. Copy shared helpers into each module, or publish
   them as a package and list it as a dependency.
2. **One folder per module**, holding `module.yaml` (or `module.yml`, never both). Put modules
   under `bentra/modules/<name>/`; `<name>` should equal `metadata.name`.
3. **`module.yaml` is the only source of the module's details**: name, display name,
   description, category, icon. There is no version in it: the version is chosen when
   publishing (strict semver, `MAJOR.MINOR.PATCH`).
4. **Keys are snake_case. Unknown keys are rejected**, except ones starting with `x-`.
   The exact schema, with descriptions and an example, is `bentra://schemas/module` (Bentra MCP
   server) or `GET /orgs/<org>/api/v1/schemas/module/`.
5. **Never put credentials in a module.** Declare them under `connection.fields` (mark tokens and
   passwords `secret: true`); people enter the values in Bentra and the action reads them from
   `$BENTRA_CONNECTION_FILE` at run time.
6. **Pin dependencies exactly** (`requests==2.32.5`, a committed `package-lock.json`).
7. **A published version never changes.** Removing an action, renaming an input or adding a
   required input is a breaking change: it needs a new major version.

## Layout

```
.github/
bentra/
  modules/
    <name>/                 # the working directory you register, e.g. bentra/modules/http-check
      module.yaml
      README.md             # any letter case; shown in Bentra's registry
      requirements.txt      # python: pinned. node: package.json + package-lock.json
      actions/
        <action>.py         # one entrypoint per action
      tests/
        <action>.json       # sample inputs for scripts/run-action.sh
  workflows/
    <workflow>/workflow.yml # workflows that call the modules (optional)
```

A repository can hold any number of modules; each is registered with its own working directory.
A repository whose root is a single module works too (working directory `""`).

## module.yaml

```yaml
apiVersion: bentra/v1
kind: Module
metadata:
  name: http-check                  # lowercase, digits, hyphens; what workflows reference
  display_name: HTTP check
  description: Check that URLs answer with the status you expect.
  category: monitoring              # infrastructure cloud data deployment security monitoring
                                    # notifications internal other
  icon: activity                    # optional Lucide icon name
runtime:
  language: python                  # python | node | bash | binary
  version: ">=3.11"                 # required for python and node
dependencies:
  file: requirements.txt            # optional
connection:                         # optional; omit when no credentials are needed
  required: false                   # false: steps may run without a connection
  fields:
    token: {type: string, secret: true, title: Bearer token}
    timeout_seconds: {type: number, default: 30}
defaults:
  timeout_seconds: 120
actions:
  - name: check_url                 # snake_case, unique
    description: Request one URL and report its status.
    entrypoint: actions/check_url.py
    timeout_seconds: 60             # optional
    inputs:                         # JSON Schema, type: object
      type: object
      properties:
        url: {type: string}
        expected_status: {type: integer, default: 200}
      required: [url]
      additionalProperties: false
    outputs:                        # JSON Schema of what the action writes
      type: object
      properties:
        status: {type: integer}
        ok: {type: boolean}
      required: [status, ok]
```

Quote YAML strings that contain `: ` or start with a special character.

## The action contract

Each action call is one process, started in a scratch directory, with these environment
variables:

| Variable | What it is |
|---|---|
| `BENTRA_INPUT_FILE` | JSON object: the step's inputs, already checked against `inputs` |
| `BENTRA_OUTPUT_FILE` | Write **one JSON object** here (at most 1 MB), matching `outputs` |
| `BENTRA_CONNECTION_FILE` | JSON object of the connection's fields. **Only set when the step names a connection**: handle it missing when `connection.required` is false |
| `BENTRA_CONTEXT_FILE` | `{run_id, job_id, workflow_id, step: {id, name, index}, module: {name, version, action}}` |
| `BENTRA_STEP_OUTPUTS` | JSON object of earlier steps' outputs, keyed by step `id` |
| `BENTRA_MODULE_DIR` | The module's files (read only) |
| `BENTRA_TEMP_DIR`, `TMPDIR`, `HOME` | A scratch directory, removed after the call |

- **Exit 0 is success**; any other exit code fails the step. On failure you may write
  `{"error": {"code": "...", "message": "...", "details": {...}}}` to the output file.
- **stdout and stderr are the step's log.** Never print connection values; secret values and
  outputs marked `x-bentra-secret: true` are masked anyway.
- **The environment is an allowlist**: only `PATH`, locale, `TZ`, proxy and CA variables come
  through. Workflow variables and secrets reach an action only as inputs.
- Don't rely on anything surviving between calls; each call starts clean.

## Runtimes

| `language` | How the runner starts the entrypoint | Dependencies |
|---|---|---|
| `python` | `python <entrypoint>` in a virtualenv per module version (runner image: Python 3.12) | `dependencies.file: requirements.txt`, pinned |
| `node` | `node <entrypoint>` (Node 22). **CommonJS only**: `.js`/`.cjs` with `require`; `import` can't see the installed packages | `dependencies.file: package.json` + committed `package-lock.json`; installed with `npm ci --omit=dev` |
| `bash` | `bash <entrypoint>`. Start with `set -euo pipefail`; use `jq` (installed) for JSON | none |
| `binary` | `bin/<os>-<arch>/<entrypoint>`, e.g. `bin/linux-amd64/sha-tool`. List each in `runtime.platforms` and commit the binaries | none (static binaries) |

## Minimal action (Python)

```python
import json, os, sys

inputs = json.load(open(os.environ["BENTRA_INPUT_FILE"]))
connection = {}
if os.environ.get("BENTRA_CONNECTION_FILE"):
    connection = json.load(open(os.environ["BENTRA_CONNECTION_FILE"]))

result = {"greeting": f"Hello, {inputs['name']}"}
print(result["greeting"])                      # the step log
with open(os.environ["BENTRA_OUTPUT_FILE"], "w") as out:
    json.dump(result, out)
sys.exit(0)
```

## Using a module in a workflow

```yaml
steps:
  - id: check                       # needed to read this step's outputs later
    name: Check the API
    module:
      name: http-check
      version: "1.0.0"              # exact and quoted
      action: check_url
      connection: monitoring-token  # a module connection shared with the workspace
      inputs:
        url: ${{ inputs.api_url }}  # form field; also steps.<id>.outputs.<key>, vars.<NAME>
  - name: Report
    run: jq '.check.status' "$BENTRA_STEP_OUTPUTS"
```

`${{ }}` expressions work only inside `module.inputs`. A value that is exactly one expression
keeps its JSON type.

## Checklist before publishing

- [ ] `module.yaml` validates against the schema; `metadata.name` matches the folder name.
- [ ] Every `entrypoint` exists inside the working directory; binaries for every platform.
- [ ] Dependencies are pinned (`requirements.txt` with `==`, committed `package-lock.json`).
- [ ] Each action reads only its env files, writes one JSON object matching `outputs`, and
      exits non-zero on failure.
- [ ] Optional connections are handled when `BENTRA_CONNECTION_FILE` is unset.
- [ ] Nothing secret in the repository or in logs.
- [ ] `scripts/run-action.sh <module dir> <action> <inputs.json>` succeeds for every action.
- [ ] `README.md` says what each action does, its inputs and outputs, and the connection.

## Registering and publishing (Bentra MCP tools)

1. `inspect_module_source` with the connector, repository, branch and working directory: shows
   the manifest, actions, README and `issues` (file, line, message, hint). Fix and repeat.
2. `register_module` with the same source. Registering publishes nothing.
3. After each push: `refresh_module`, then `validate_module` (the full publish checks, no
   release) and poll `get_module_publication`.
4. Ask the user for the version, then `publish_module_version` with `expected_sha` set to the
   commit you validated. Poll `get_module_publication` until `published`.
5. Create a connection with `create_module_connection` (non-secret fields only; the user enters
   secrets in Bentra), then reference the module from `workflow.yml`.
````

## 2. Connect the Bentra MCP server

With the [Bentra MCP server](/ai/mcp-server) connected, the agent can check its work against your organization instead of guessing:

| The agent needs | MCP |
|---|---|
| The exact manifest schema, with descriptions and an example | resource `bentra://schemas/module` |
| The registry workflow and the action contract | resource `bentra://guides/modules` |
| To see what Bentra finds in a folder, with problems by file and line | `inspect_module_source` |
| To register, re-check and validate without publishing | `register_module`, `refresh_module`, `validate_module` |
| To publish once you agree on a version | `publish_module_version` |

The agent can't set connection secrets: you enter those in Bentra.

## 3. Ask for the module

A prompt that works well. Replace the parts in angle brackets:

```text Prompt
Create a Bentra module in bentra/modules/<name> that <what it should do>.

Actions:
- <action_name>: <what it does>. Inputs: <inputs>. Outputs: <outputs>.

It talks to <service> and needs these credentials: <fields>, from a Bentra connection.
Write it in <Python | Bash | Node.js | Go>.

Follow AGENTS.md. Read bentra://schemas/module before writing module.yaml. Add sample
inputs under tests/ and run every action with scripts/run-action.sh. Then call
inspect_module_source on the branch you pushed and fix every issue it reports. Don't
register or publish until I confirm.
```

## 4. Review before you publish

Publishing is permanent, so check the agent's work against the checklist at the end of `AGENTS.md`, then:

<Steps>
<Step title="Review it in Bentra">
**Modules → Register module** (or `inspect_module_source`) shows the module, every action's inputs and outputs and the README, exactly as Bentra will package them.
</Step>
<Step title="Validate">
Register it, then **Publish new version → Validate** (or `validate_module`) runs every publish check without releasing anything.
</Step>
<Step title="Publish">
Choose the version yourself. A removed action or a new required input is a breaking change and needs a new major version.
</Step>
</Steps>

## Why it's set up this way

- **One folder per module.** The agent works in one directory, and nothing it writes elsewhere can change the module.
- **The schema is the source of truth.** It is served by your own Bentra, so it always matches what Bentra accepts.
- **Plain files in and out.** Inputs, outputs and the connection are JSON files, so an agent can run and test an action locally without Bentra or a runner.
- **Problems come back with a file, line and hint**, which an agent can fix without a person explaining.
