---
title: "module.yaml syntax"
description: "Every field of a module's manifest: metadata, runtime, dependencies, connection and actions."
---

Each module has a `module.yaml` (or `module.yml`, not both) at the top of its working directory. Bentra validates it whenever it reads the source and again when it builds a release. Keys are snake_case; unknown keys are rejected, except ones starting with `x-`. The same schema, with descriptions and an example, is served at `GET /orgs/{org}/api/v1/schemas/module/` and as the MCP resource `bentra://schemas/module`.

```yaml
apiVersion: bentra/v1
kind: Module
version: 1.2.0
release_notes: Adds expected_status to check_url

metadata:
  name: http-check
  display_name: HTTP check
  description: Check that URLs answer with the status you expect.
  category: monitoring
  icon: activity
  docs: README.md

runtime:
  language: python
  version: ">=3.11"

dependencies:
  file: requirements.txt

connection:
  required: true
  fields:
    token: {type: string, secret: true, required: true, title: API token}
    base_url: {type: string, default: "https://api.example.com"}

defaults:
  timeout_seconds: 300

actions:
  - name: check_url
    description: Request one URL and report its status.
    entrypoint: actions/check_url.py
    timeout_seconds: 120
    inputs:
      type: object
      properties:
        url: {type: string}
      required: [url]
    outputs:
      type: object
      properties:
        status: {type: integer}
```

Unknown fields are errors, so a typo is caught. For your own notes, use keys starting with `x-`.

## Top level

| Field | Required | Value |
|---|---|---|
| `apiVersion` | yes | `bentra/v1` |
| `kind` | yes | `Module` |
| `version` | yes | The module's version, `MAJOR.MINOR.PATCH` or a pre-release like `1.3.0-rc.1`, no `v`. Bump it to release: see [Versions and releases](/modules/publishing) |
| `release_notes` | no | What changed in this version, up to 5,000 characters. Stored with the release |
| `metadata` | yes | See below |
| `runtime` | yes | See below |
| `actions` | yes | One or more actions |
| `dependencies` | no | Packages to install |
| `connection` | no | The credentials and settings the module needs |
| `defaults` | no | `timeout_seconds` for actions that don't set one |

Bentra releases each `version` it hasn't released yet. Changing files without bumping `version` releases nothing.

## metadata

The registry shows these exactly as written; they can't be edited in Bentra. Change them here and check for changes.

| Field | Required | Value |
|---|---|---|
| `name` | yes | What workflows reference. Lowercase letters, digits and hyphens, starting with a letter, 2 to 63 characters. Unique in your organization; can't change after registering |
| `description` | yes | One or two sentences, up to 500 characters |
| `display_name` | no | The name shown in the registry |
| `category` | no | `infrastructure`, `cloud`, `data`, `deployment`, `security`, `monitoring`, `notifications`, `internal` or `other` |
| `icon` | no | An icon name, such as `cloud` |
| `docs` | no | Path to a Markdown file in the working directory, shown on the module's page. Without it, `README.md` at the top of the working directory is used, in any letter case |

## runtime

| Field | Required | Value |
|---|---|---|
| `language` | yes | `python`, `bash`, `node` or `binary` |
| `version` | for `python` and `node` | `"3.12"` (any 3.12.x) or `">=3.11"` (that version or newer) |
| `platforms` | for `binary` | Platforms you ship a program for: `linux-amd64`, `linux-arm64`, `darwin-amd64`, `darwin-arm64`, `windows-amd64`, `windows-arm64` |

## dependencies

| Field | Value |
|---|---|
| `file` | Python: a requirements file. Node: `package.json`, with `package-lock.json` beside it |

Only `python` and `node` modules can declare dependencies.

## connection

| Field | Required | Value |
|---|---|---|
| `fields` | yes | One entry per field, keyed by its name (lowercase letters, digits, underscores) |
| `required` | no | `false` lets a step call the module without a connection. Default `true` |

Each field:

| Field | Required | Value |
|---|---|---|
| `type` | yes | `string`, `number` or `boolean` |
| `secret` | no | `true` for credentials: encrypted, never shown again, masked in logs |
| `required` | no | `true` if a run can't start without it |
| `default` | no | Used when the connection doesn't set the field. Not allowed on secret fields |
| `title`, `description` | no | Shown on the connection form |

## actions

| Field | Required | Value |
|---|---|---|
| `name` | yes | Lowercase letters, digits and underscores, starting with a letter. Unique in the module |
| `description` | yes | What the action does |
| `entrypoint` | yes | Path to the file to run, inside the module's folder. For `binary`, the program's name under `bin/<platform>/` |
| `timeout_seconds` | no | 1 to 86400 |
| `inputs` | no | JSON Schema for the inputs |
| `outputs` | no | JSON Schema for the outputs |

`inputs` and `outputs` are [JSON Schema](https://json-schema.org/) (draft 2020-12) and must have `type: object`. References must be local (`#/$defs/...`). Add `x-bentra-secret: true` to an output property to mask its value in logs.

```yaml
inputs:
  type: object
  properties:
    name:
      type: string
      description: Name of the workspace.
    auto_apply:
      type: boolean
      default: false
    tags:
      type: array
      items: {type: string}
  required: [name]
  additionalProperties: false
```

With `additionalProperties: false`, a workflow that passes an input the action doesn't know is rejected when the workflow is published.

## Changes to this format

A released version is never checked again against a newer format. `version` became required in `bentra/v1` when releases moved into `module.yaml`.
