title: "Connectors"
---

A connector gives Bentra access to the Git provider that holds your workflows. Only **GitHub** is supported today. Add connectors under **Settings → Connectors**, and click one to see its details, rotate its credentials, test it, and change its maintainers and the workspaces that can use it.

## Who manages and uses a connector

Two separate lists decide this, both on the connector's page:

- **Maintainers** are the users and groups that manage the connector: edit it, rotate or test its credentials, change where it's used, and delete it. Whoever adds a connector becomes its first maintainer. Owners and admins can always manage every connector.
- **Workspaces** are where workflows can use it: the workspaces on its list, or **every workspace** in the organization. People in those workspaces can pick the connector in their workflows but can't change it.

When you add a connector, **Available in** defaults to the workspace you're in. Add more workspaces and maintainers from its page afterwards.

| | Owners and admins | Members |
|---|---|---|
| Add a connector | Available in any workspace, or every workspace | Available in a workspace they belong to |
| Change, rotate, share or delete it | Any connector | Connectors they maintain, directly or through a group |
| Add a workspace | Any workspace | Workspaces they belong to |
| Make it available in every workspace | Yes | No |

Any member of a workspace a connector is available in can select it. A group maintainer covers whoever is in the group, so a team keeps managing its connector when people join or leave. If a connector has no maintainers left, only owners and admins can change it.

You can't remove a workspace from a connector, or delete it, while workflows there still use it. The connector page lists them under **Used by**; switch them to another connector first. Deleting a workspace just removes it from its connectors' lists.

Bentra uses a connector to:

- list repositories and branches/tags when you create a workflow
- read the repository when a workflow syncs, and find `workflow.yml`, `form.yml` and the README in the workflow's [working directory](#repository-layout)
- hand a token to a runner so it can clone the repository; a runner only gets it for a run its pool is executing
- commit form edits made in Bentra to a branch and open a pull request
- trigger GitHub Actions workflows from a [`github_workflow_dispatch`](/reference/workflow-syntax#github-actions-steps) step

## Repository layout

A repository workflow has one path setting, its **working directory**: the folder that holds its files. Empty means the repository root. Set it when you create the workflow or under the workflow's **Settings → Source**. Bentra finds the files there by name:

| File | Accepted names | Needed |
|---|---|---|
| Workflow | `workflow.yml`, `workflow.yaml`, `WORKFLOW.yml`, `WORKFLOW.yaml` | Always |
| Form | `form.yml`, `form.yaml`, `FORM.yml`, `FORM.yaml` | Request workflows. Ignored for jobs. |
| README | `README.md`, `readme.md` | Optional |

One repository, and one connector, can serve several workflows, each with its own working directory:

```text
inventory/workflow.yml  inventory/form.yml  inventory/README.md
release/workflow.yml    release/form.yml
tools/common.sh
```

Steps start in the working directory, and the run has the whole repository, so a step in `inventory/` can run `../tools/common.sh`.

A sync fails, and the version published before keeps running, when:

| Error | Fix |
|---|---|
| `The working directory 'x' isn't in the repository.` | Correct the working directory, or add the folder on the tracked branch or tag. |
| `No workflow.yml or workflow.yaml in the working directory 'inventory'.` (or `... in the repository root.`) | Add the file under one of the accepted names. The same applies to `form.yml` on a request workflow. |
| `inventory/form.yml and inventory/form.yaml are both present. Keep one of them.` | Delete one of the two files. |

If your repository still uses the older per-file path settings, follow the [migration steps](/guides/bentra-stored-workflows#moving-from-bento-paths).

## GitHub App (recommended)

Install the app on the repositories your workflows use, not on the whole organization. Bentra and its runners only ever use installation tokens, which expire after an hour.

| Permission | Access | Why |
|---|---|---|
| Metadata | Read | Required by GitHub for every app |
| Contents | Read and write | Read workflow and form files; clone for runs. Write only commits form edits to a branch |
| Pull requests | Read and write | Open a pull request for a form edit |
| Actions | Read and write | Only for [`github_workflow_dispatch`](/reference/workflow-syntax#github-actions-steps) steps: trigger a workflow and follow its run |

If you don't edit forms from Bentra, **Contents: Read** and no pull request access are enough. Without `github_workflow_dispatch` steps, the app needs no Actions access.

For a `github_workflow_dispatch` step, the target repository must belong to the connector's owner, and the app must be installed on it. The runner gets a token limited to that one repository, with **Actions: Read and write** and **Metadata: Read** only.

## Personal access token

Use a **fine-grained** token limited to the same repositories, with the permissions in the table above. A classic token with `repo` scope works but grants access to every repository the user can see. The token acts as its owner, so prefer a dedicated machine user. Runners receive the token itself to clone, and a `github_workflow_dispatch` step uses the same token unchanged, so it can't be narrowed to one repository. That's another reason to prefer the GitHub App.

## Storage

Connector credentials are encrypted with your organization's own data key before they are stored.
