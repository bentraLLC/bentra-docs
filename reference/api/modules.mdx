title: "Modules"
---

[Modules](/modules/overview) are reusable packages of actions your organization releases for its workflows. These endpoints cover the registry, releases and versions.

**Versions come from `version` in the module's `module.yaml`.** Registering a module, refreshing it (`POST modules/{id}/refresh/`), a push to its branch or tag and Bentra's regular check all read the source, and each one releases the version `module.yaml` declares if Bentra hasn't released it yet. No endpoint takes a version to release, and a released version can't be changed. See [Versions and releases](/modules/publishing).

**Permissions:** every member can read the registry (`org.view_modules`) and register modules (`org.create_modules`). A module's maintainers, and owners and admins (`org.manage_modules`), can change its source, validate it, deprecate or revoke versions, choose the active version, archive and delete it. Releases come from the repository: anyone who can push to the module's branch or tag can release it.

## A module

```json
{
  "id": "…",
  "name": "http-check",
  "display_name": "HTTP check",
  "description": "Check that URLs answer with the status you expect.",
  "category": "monitoring",
  "status": "active",
  "active_version": {"version": "1.2.0", "status": "published", "sha256": "…", "published_at": "…"},
  "active_version_pinned": false,
  "auth": {
    "required": false,
    "methods": [
      {
        "id": "token", "type": "token", "title": "Token", "description": "Sent as a bearer token.",
        "fields": [{"name": "token", "type": "string", "secret": true, "required": true, "title": "Token", "description": ""}]
      }
    ]
  },
  "source": {
    "connector_id": "…",
    "repository": "acme/automation",
    "ref": "main",
    "ref_type": "branch",
    "working_directory": "bentra/modules/http-check",
    "source_sha": "9f2c…",
    "validated_sha": "9f2c…",
    "validation_state": "valid",
    "issues": [],
    "version": "1.2.0",
    "version_released": true,
    "readme": "# HTTP check\n…"
  },
  "can_manage": true
}
```

`name` comes from the module's `module.yaml` and never changes. `active_version` is the version the registry shows and new workflow steps use: the newest release unless a maintainer pinned one (`active_version_pinned`); `null` until the first release finishes. `source.version` is what `module.yaml` declared at the last check and `source.version_released` whether Bentra has released it. `source.validation_state` is `valid`, `invalid`, `unreachable` or `unknown`.

`auth` is what a workflow step passes in [`module.auth`](/modules/use-in-workflows#authentication): whether it is `required`, and each accepted method with its `id` (what the step writes as `type`) and fields. It comes from the active version's `module.yaml`. Bentra stores no credentials for a module.

Reading a module never contacts the repository. `source` shows what the last refresh saw.

## Register a module

Bentra reads only the module's working directory and what is nested in it.

```http
POST modules/inspect/
{"connector_id": "…", "repository": "acme/automation", "ref": "main",
 "ref_type": "branch", "working_directory": "bentra/modules/http-check"}
```

returns what that folder holds, without registering anything:

```json
{"commit_sha": "9f2c…", "registered_as": null,
 "inspection": {"valid": true, "manifest_file": "module.yaml", "manifest": {…},
                "actions": [{"name": "check_url", "description": "…",
                             "inputs": [{"name": "url", "type": "string", "required": true, "description": "…"}],
                             "outputs": [{"name": "status", "type": "integer", "required": false, "description": ""}]}],
                "readme": "# HTTP check…", "readme_html": "<h1>…</h1>",
                "file_count": 4, "files": ["README.md", "actions/check_url.py", "module.yaml", "requirements.txt"],
                "issues": []}}
```

`registered_as` names the module already registered from this folder. `files` lists at most 200 paths.

```http
POST modules/
{"connector_id": "…", "repository": "acme/automation", "ref": "main",
 "ref_type": "branch", "working_directory": "bentra/modules/http-check"}
```

returns `201` with the module, or `422` with `issues` when the source isn't valid. The name, display name, description, category and icon come from `module.yaml`; sending any of them is a `400`. The module's `source.readme` holds the README Bentra last read.

## Issues

Validation problems come back as a list:

```json
{"code": "entrypoint_missing", "message": "actions/wait_for_run.py does not exist in the module directory.",
 "file": "module.yaml", "line": 31, "field": "actions[2].entrypoint",
 "hint": "Add the file or fix the path.", "severity": "error"}
```

`severity` is `error` or `warning`. Warnings don't block a release. `version_not_bumped` (a warning) means the module's files changed but `version` didn't, so nothing was released.

## Releases

Each release or validation is a publication. List them (newest first) with `GET modules/{id}/publications/`:

```json
{"id": "…", "status": "published", "requested_version": "1.2.0", "trigger": "push",
 "dry_run": false, "commit_sha": "9f2c…", "version": "1.2.0", "issues": [],
 "requested_by": null, "created_at": "…", "finished_at": "…"}
```

| Field | Notes |
|---|---|
| `status` | `pending`, `running`, `published`, `validated` (a validation that passed) or `failed` |
| `trigger` | `register`, `refresh` (Check for changes), `push`, `poll` (Bentra's regular check) or `validate` |
| `requested_version` | The version `module.yaml` declared at `commit_sha` |
| `error_kind` | On failure: `invalid` (with `issues`), `source_moved` (`module.yaml` no longer said that version at the commit), `version_exists`, `auth`, `not_found` or `unavailable` |

**Validate** runs every release check on the current source and releases nothing:

```http
POST modules/{id}/publications/
{"dry_run": true}
```

returns `202`; poll `GET modules/{id}/publications/{publication_id}/` until it is `validated` or `failed`. Sending a `version` is a `400`: releases come from `module.yaml`. `409` while another release or validation of the module is running.

## Active version

```http
POST modules/{id}/versions/1.1.0/activate/     # make 1.1.0 active, and keep it through later releases
POST modules/{id}/follow-newest/               # follow the newest release again
```

Both return the module. Workflows keep the exact versions they pin.
